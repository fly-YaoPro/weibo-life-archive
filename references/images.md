# 图片完整下载与验收

这是一份图文手账，不是先交纯文字、等用户再催才补几张图。图片采集、图片理解、页面选图是三个不同环节。要求对所有模型和宿主一致，不绑定具体产品、套餐或工具名。

## 1 先盘点源图，不以本地已有数量为分母

- 每条实际交付微博核对 `pic_num`、详情页相册或可靠导出的原图清单，填写 `expected_image_count`、`image_inventory_status`、`image_count_basis`。`image_count_basis` 写明核对来源与结果，例如“详情页相册12张，已逐张枚举”，不能只写“已下载4张”。
- 已确认没有图片才填0。未展开、解析失败或数量未知填null，状态为unknown/partial，保留待补任务；不能删除images或改成0绕过检查。记录本身没有正文但有有效图片时，保留真实缺文状态，不编文字。
- 多图按源图ID保存全部条目，失败的图片也留位置、源URL、原因和重试状态。`pic_num`大于列表已得数量时补详情，尤其检查超过9张的微博。转发、视频封面、头像、平台图标不混充原创配图。
- `records.json`放本轮实际交付的记录：完整模式收录范围内的记录，精选模式收录入选记录。未入选候选留cache/，不能混入页面又以“未入选”为由不下图。

## 2 以图片帮助选材，不是所有照片平铺首页

精选时先看候选是否有图、图文表达的事件是否具体。按月份/年份寻找旅行、学习、作品、物件、日常关系等有证据的片段；能看缩略图时实际看图，不能只按“毕业、旅行”几个词筛。每个有图年份与主要生活主题尽量有合适的图片来源，不机械设配图比例或为凑数量加入无关图。

普通日常和有价值的纯文字都保留。不能只选高赞、只选最新几条、同一趟旅行重复占满，也不能把照片里的路人、商品、转述推断成当事人经历。若候选确实以纯文字为主，如实说明已找过哪些范围；不制造“历史照片”。

下载覆盖和页面展示分开：一条入选微博有18张图，就保存18张，主题页可以只展示其中2—3张；其余仍在档案和大图浏览中可用。

## 3 正常权限内逐张下载，失败有后续

使用宿主允许的浏览器下载/文件能力；经过小样本验证且宿主允许时，可用对应源URL下载。无需固定浏览器品牌或MCP，不能提取或复制凭据来迁就脚本。

1. 枚举源图ID与真实URL，建立完整下载队列，按记录ID/图片序号保存，不由模型手写几条代表图URL代替全队列。小图约360px；大图争取约2000px，不默认保存原始超大图。
2. 保守低并发，成功一张记录一张；校验实际文件字节、格式、尺寸及来源对应，不只看退出码或HTTP 200。文件以真实格式保存，空文件、登录页、风控HTML、占位图不算成功。
3. 普通网络超时等短暂问题最多重试2次，保留成功文件和失败清单。失效URL可回原详情页取得新URL；不能无限重试或换身份绕过平台限制。
4. 若接口能读文字但拿不到图片，回源详情页展开相册，使用浏览器正常保存图片；大图不行则检查平台实际提供的最大可用规格。正常下载确有困难时，可接受对应真实图片元素的高分辨率截图作为最后的补救，并明确标记截图来源与实际尺寸，不能以整页含UI截图冒充平台大图。截图不是完整双规格下载，不将未取得的规格报成功。
5. 平台仅提供较小图片时保存真实最大可用图，写 `large_note` 说明已核对的规格限制；可将它同时用于缩略图与大图入口，不能上采样后谎称2000px。相同文件不说明原因会被检查器拦截。
6. 登录失效、验证码、403/429、持续空响应或限流时保存进度并暂停，请用户处理；源图删除/确实不可见时逐条报告。保留真实正文和失败项，但不能把缺图当成完整交付。授权不支持强行绕过访问限制。

按失败队列续跑，只补未齐图片或规格，不重采全部正文，不覆盖用户已有数据。首次不下载、被催后只下载4张、再请用户指定剩余照片，都不属于完成流程。

## 4 字段与机械门禁

每条实际收录记录：

```json
{
  "expected_image_count": 2,
  "image_inventory_status": "complete",
  "image_count_basis": "详情相册2张，与源图ID清单一致",
  "images": [{
    "image_id": "真实源图PID或稳定图片ID",
    "origin": "platform",
    "source_url": "https://平台提供的真实图片URL",
    "thumb_path": "images/记录ID/01-small.jpg",
    "large_path": "images/记录ID/01-large.jpg",
    "download_status": "saved"
  }]
}
```

示意省略了第二张条目，实际必须有2项。`origin:user_provided`时用`provided_reference`说明用户授权真实资料来源。`image_inventory_status`只在枚举核对完成时设complete；数量未知不能靠填入images长度来“确认”。源图本身分辨率低、两规格相同的，在该图加`large_note`写明源端限制与已核对情况。

运行：

```bash
python scripts/audit_images.py "项目目录"
python scripts/check_project.py "项目目录" --kind weibo --stage data
```

任一条数量未知、清单少于源图、某图未保存/缺规格、文件不符合可识别图像结构，退出非零；不能只运行旧检查器或跳过失败项。构建器也调用同一门禁，不能先输出“完成版”再把图片列为“后续可补充”。图片被删或受限时停在数据/缺口交付，等待补采或用户调整任务。

`audit_images.py`只做本地容器、路径、数量和哈希检查，不联网，不读取登录态。它无法证明清单等于平台真总数，也不代替完整图片解码或人工看图。JPEG/GIF/WebP做容器级结构核验，PNG另核对chunk CRC；平台给AVIF等当前未支持格式时，使用宿主正常读图/转换能力保存可验证的真实图片副本，保留源文件与转换说明，不伪装文件后缀。

## 5 交付前从源到页面抽查

- 对照源页核对不同年份、有图、纯文字、超过9图各类记录；不得以本地images长度自证源数量。
- 核对“源端应收图片数／已完整保存图片数／未知总数的微博数／缺失规格与原因”，例如应收117张、实存4张就是未完成，不写“新增4张，带图版已完成”。
- 真实看图，确认大图可解码、图文匹配，尤其正文无明显地名/事件线索的照片；不能只扫文件名。总览及有合适图的主题实际展示照片，日历能查阅每条全部配图，不能所有主题仍纯文字。
- 构建成功会附`image-audit.json`，包括逐图尺寸、字节数与SHA-256；原始资料和续跑清单继续保留。交付时只给简短汇总，不把大份技术清单塞进个人总结。
